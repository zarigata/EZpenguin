Overview

EZpenguin is a Debian-minimal derivative built with a fully scripted, Docker-based pipeline. Every artifact is produced inside a container, keeping the build steps consistent across supported hosts. Package mirrors and build timestamps can change the output; bit-for-bit reproducibility is not yet guaranteed.

│  HOST (macOS / Linux / CI)                                  │

│                         ▼                                   │
│              6. PACKAGE → rootfs tarball / IMG (build/image.sh)│

│                         │                                   │
│                         ▼                                   │
│              7. VERIFY  → QEMU boot tests (BIOS+UEFI+ISO)   │
│                         → interactive wizard smoke test     │
└─────────────────────────────────────────────────────────────┘

Layers

1. Base layer — Debian

  • Suite: bookworm (Debian 12)
  • Variant: minbase via debootstrap, then curated package set
  • Rationale: Debian stability + massive package universe; a package ecosystem available on x86-64 and ARM64.

2. EZpenguin layer

Everything that makes it *EZpenguin* lives in rootfs-overlay/ and scripts/:

PathPurpose
/etc/ezpenguin/Distro identity, config, version
/usr/local/bin/ez-*User-facing CLI tools
/etc/apt/sources.list.d/Repo pinning (Debian + EZpenguin)
ezpenguin-firstboot.serviceFirst-boot wizard (systemd)
ezpenguin-installerBare-metal installer frontend

3. Build pipeline

  • build/build.sh — orchestrator; single entry point
  • build/rootfs.sh — creates the rootfs inside Docker (native or foreign

arm64 debootstrap under qemu-user-static)

  • build/image.sh — flashable disk image: amd64 = GPT BIOS-boot + ESP +

root with GRUB for BIOS and UEFI; arm64 = GPT ESP + root, arm64-efi GRUB. Static UUID grub.cfg (deterministic, no build-time device paths)

  • build/iso.sh — hybrid live ISO: squashfs live root (live-boot),

grub-mkrescue layout, El Torito BIOS + UEFI records, size-budgeted

  • build/Dockerfile — pinned build environment

3a. Live ISO design

ISO (hybrid, BIOS El Torito + UEFI El Torito + isohybrid MBR)
├── /boot/vmlinuz-*, /boot/initrd.img-*   (live-boot-enabled initramfs)
├── /boot/grub/grub.cfg                   (boot=live, serial console)
└── /live/filesystem.squashfs             (xz-compressed full rootfs)

On boot, live-boot scans devices, mounts the squashfs as the root (overlayfs), systemd starts, and the wizard detects boot=live on the kernel command line to offer disk installation via ez-install.

3b. Disk layout (amd64)

GPT: p1 1M   ef02 BIOS-boot   (GRUB i386-pc core)
     p2 260M ef00 ESP         (FAT32, EFI/BOOT/BOOTX64.EFI)
     p3 rest 8300 root        (ext4, LABEL=EZP_ROOT)

arm64 drops p1 (UEFI-only: ESP + root).

All steps are idempotent and fail fast. Exit code != 0 stops the line.

4. QA layer

Tests run *inside* the built rootfs (via chroot) before any artifact is packaged. A build that fails tests produces no output. See TESTING.md.

Design principles

  1. Scripted — a versioned build pipeline with no manual image assembly.

Bit-for-bit reproducibility requires additional dependency and timestamp pinning.

  1. Minimal — nothing in the base that isn't required or explicitly chosen.
  2. Tested — untested = broken. Every build runs the full QA suite.
  3. Boring — prefer proven Debian defaults over cleverness.
  4. Automated — first-boot wizard, not install-time questions where avoidable.

First-boot flow (automated)

power on → systemd → ezpenguin-firstboot.service
  ├─ detect hardware (board/PC/VM)
  ├─ expand root filesystem
  ├─ ask: locale, timezone, keyboard, hostname, user, password
  ├─ apt update && upgrade
  ├─ (optional) install software sets
  └─ reboot → ready

Versioning

MAJOR.MINOR.PATCH — e.g. 1.0.0. Tracked in config/ezpenguin.cfg and stamped into /etc/ezpenguin/version at build time. Artifacts embed the version in their filename.
